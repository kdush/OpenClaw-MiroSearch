## 2. 失败与「达标」的判定口径

判定**只看无 429、且 pipeline 正常跑完**的用例；限流与内容审核一律单独归类，
不计入质量通过，也不计为代码回归（路线图 §7 与本次任务要求）。

按此口径，**10 个「达标」里有 3 个需要限定，不能当作质量通过来读**：

| 用例 | 限定 | 依据 |
|---|---|---|
| **A** | 未触发检索 | light 档下模型直接作答（`search_rounds=0`），与基线记录的同一行为一致。它验证的是「简单事实题跳过检索」，不是检索质量 |
| **D1** | 检索根本不可达 | `searxng-only` + `SEARCH_PROVIDER_ORDER_STRICT=1` + `SEARXNG_BASE_URL=http://127.0.0.1:27080`，本机无 docker → 12 次尝试、0 轮成功（`search_provider_hits={"searxng":10}`）。它只证明「不可达时按严格路由诚实降级、不崩」，**没有验证任何检索质量** |
| **H5A** | 门禁为空转 | H5A 的门禁是 `profile_compare`，按设计**只记录结构、不做判定**（成对结论由 H5A/H5B 对比给出）。而 H5B 本轮被限流打穿，**这对对比因此不完整**。同时 H5A 同样指向不可达的 SearXNG（14 次尝试、0 轮、0 抓取、0 注册表条目） |

**因此真正的质量通过是 7 个：C、D2、E1、H2、H3、L1、L3**，其中 4 个（H2/H3/L1/L3）
跑的是**硬门禁且全过**（`hotspot_detailed`：结构完整、有冲突章节、有置信度标记、
有内容分析、有 mermaid 拓扑、无诊断噪声泄漏、无截断 URL 桩、无裸 pending 线索状态）。

## 3. 门禁失败：H4

`hotspot_compact` 门禁失败，唯一失败项 `compact_missing_uncertainty_hedge`。

- **不是限流**（`429=0`），也不是代码缺陷——**门禁按设计正常工作**。
- 根因在模型侧：compact 报告的正文只有 **129 字符**（`## 结论` 一小段 + 空的
  `## 证据与来源`），交付文本 3776 字符里约 3647 字符是**后处理补的 References**。
  正文既没有不确定性措辞（不确定/未证实/冲突/分歧…），又对争议话题直接标注
  「置信度：高」——正是该门禁要拦的形态。
- 该用例 baseline 未跑，**无可对比基线**。

## 4. 内容审核拦截：L2

失败项 `Final summary produced no usable answer.`，但 `429=0`、`timeout=0`。
查原始日志，真实原因是**提供商侧内容审核**：

```
400 - {'contentFilter': [{'level': 1, 'role': 'user'}],
       'error': {'code': '1301', 'message': '系统检测到输入或生成内容可能包含不安全或敏感内容…'}}
```

连续 21 次触发后触发 `LLM Failure Guard: Exceeded max consecutive LLM failures (6)`，
主循环终止。L2 的题目是「近两周有明显对立叙事的中文网络舆情事件（非娱乐八卦）」，
而 L1（娱乐八卦）与 L3（科技/AI 谣言）同批均正常完成——**拦截与代码无关**。

> **工具侧的诚实说明：** `run_metrics` 只统计 429 与各类 timeout，**不统计内容审核拒绝**，
> 所以本类失败无法只靠 `acceptance_results.json` 判出，需要回查原始日志。
> 这里**故意没有**给 harness 加「按提供商文案匹配」的计数器：本仓库的架构约束是
> **不绑定特定 LLM 提供商**，判定只允许用协议层信号（状态码/标准字段名），而
> `contentFilter`/`1301` 是提供商专有文案。**建议后续单独立项**，用一个提供商中立的
> 口径（如「400 且非 context-length」）补上这一类计数。

## 6. §7 指标与基线对比（可归因性声明）

对比对象：`docs/acceptance/baseline-2026-09-24/`（阶段 A 冻结，**3 个用例**：A/B/H1）。

| 指标 | 基线（3 例） | 候选（16 例） |
|---|---|---|
| p50 / p95 耗时(s) | 339.6 / 427.8 | 233.9 / 440.1 |
| LLM 调用 / 输入 token / 输出 token | 26 / 276956 / 32151 | 175 / 1081011 / 32706 |
| 检索次数 / 抓取次数 | 24 / 9 | 124 / 35 |
| 无依据数字 / 错误引用数 | 8 / 0 | 28 / 0 |

### 6.1 为什么这组数字不能用来宣称提升

1. **模型不同**（归因硬阻断）：基线 `glm-5.3-flash`（付费）vs 候选 `glm-4.5-flash`（免费）。
   本账号付费额度已耗尽（付费模型 `429 code 1113`），**无法在同一模型下复跑基线**。
2. **用例集不同**：基线只有 3 例，候选 16 例；运行级汇总（总耗时、总 token、总检索）
   因用例数不同而不可比。
3. **「无依据数字 8 → 28」是用例集变化的产物，不是回归**：基线的 8 全部来自 H1；
   候选的 H1 被限流打穿（计 0），而 28 来自基线从未跑过的用例
   （H2 8、L2 8、L3 6、H3 5、L1 1）。
4. **两项指标只覆盖跑门禁的用例**：`无依据结论数` 与 `错误引用数` 取自门禁的
   `structure_metadata`，而门禁只在 hotspot 用例上跑。A–E/L 组没有门禁 →
   这两项对它们是**「未测量」而非 0**，基线的 B 同样是「未测量」。
5. **供应商费用未回填**：按基线文档约定人工从控制台读取，工具不估算。

### 6.2 工具判出的方向性回归（逐条解读）

`compare_acceptance_runs.py` 在排除不可比用例后报出 **2 项**，都在用例 A：

| 项 | 基线 → 候选 | 解读 |
|---|---|---|
| A: input_tokens | 8008 → 8202（+194） | 提示词/配置增大带来的**轻微成本上升**；A 两轮都未检索、行为一致。方向由「模型差异 + #2 新增配置」共同造成，**不可单独归因于代码** |
| A: output_tokens | 34 → 101（+67） | 同上 |

**B 与 H1 的 8 项「回归」已被工具排除**：它们候选未跑完，数字反映中断状态
（耗时变长、检索/抓取/来源数失真），属于环境容量阻塞。工具现在会显式列出
「不可比用例」，不再把限流算成代码回归（修复见 §7）。

## 7. 本轮发现并修复的缺陷（都在验收工具链内）

运行与对比过程中发现 5 处**工具缺陷**，均已用最小复现 + 定向测试修复；
**未改动任何产品代码**。

| # | 位置 | 缺陷 | 影响 |
|---|---|---|---|
| 1 | `run_acceptance_live.py` | `has_claim_topology` 用注入前的 `raw_summary` 判定，且与「证据缺口」相与 | Q4 落地证据被系统性漏记：16/16 用例判为 `False`。改为判**交付文本**，并拆出 `has_claim_gap_node` 与 `has_claim_topology_raw` |

| 3 | `compare_acceptance_runs.py` | `registry_entries` 直接 `len(source_registry)` | 真实形态是 `{"entries": [...], "next_source_id": N}` → **每个用例都报 2**，把 M1 的主要量化收益漏记（应为 28/30/49…）。测试夹具用的是另一种形态，所以单测没暴露 |

| 5 | `compare_acceptance_runs.py` | 回归判定不区分「候选未跑完」 | 把限流打穿的 B/H1 共 8 项算成**代码回归**，与「不要把限流算成代码回归」的要求直接冲突。改为单列「不可比用例」并排除出判定 |

## 8. 未覆盖 / 受限项（如实列出）

1. **归因结论缺失**：模型不同 + 用例集不同 → 无法宣称「代码改动带来提升」。
   需要付费额度（或低峰时段 + 同模型复跑基线 A/B/H1）才能补齐。
2. **4 个 deep/hotspot 用例被限流打穿**：B、E2、H1、H5B。需重跑。
3. **H5A/H5B 成对对比不完整**：H5B 限流失败，profile 对比结论缺一半。
4. **依赖 SearXNG 的路径全部未真正验证**：D1、H5A（本机无 docker）。
5. **供应商费用未回填**（需控制台人工读数）。
6. **`无依据结论数`/`错误引用数` 对非 hotspot 用例是「未测量」**，不是 0。
7. **内容审核拦截（L2）无法从产物直接判出**，需回查原始日志；见 §4 的后续建议。
8. **本轮未触碰**：P1 图像证据管线、路线图暂缓项 D1–D3（**注意与验收用例 D1/D2 同名但无关**）。
9. **M3 默认启用范围维持现状**（只在 deep 档默认开启）——在质量与成本边界有数据前不扩大。
