## 1. 对标对象概要

jev-search 是一个自然语言网页搜索引擎：LLM 解析用户意图 → 自动推演搜索词、数据源与时间范围 → 经 Search1API 并发检索多引擎 → 输出带相关性分数的链接与摘要。**明确承诺不生成总结性答案。**

与本文相关的工程特性：

| 特性 | jev-search 的做法 | 所在模块 |
|---|---|---|
| 多源并发 | Google/DuckDuckGo/Yandex/HN/Reddit/GitHub/X/arXiv/YouTube/Wikipedia/IMDb/WeChat 并行探测；单路限时 15s、全局 30s；单路超时不阻断全局 | `pipeline.ts` |
| 引擎路由 | 支持站点清单、引擎路由表、时间粒度配置独立维护 | `sources.ts` / `candidates.ts` |
| 猜测性请求 | 意图解析完成前即可预启 Google 搜索 | — |
| 共识度排序 | 结果按 URL 归一去重后，依「相关性 + 跨引擎共识度 + 原榜单位置」三维加权；低分结果隔离 | `rank.ts` / `merge.ts` |
| 供应商容错 | 三级模型供应商池（TypeSafe / Vercel Gateway / CF Workers AI），仅 402/429/5xx 触发软切换；支持预算熔断 | `judge-config.ts` |
| 缓存 | KV 按派生哈希存中间态，TTL 随查询时间窗浮动（10 分钟–6 小时） | `cache.ts` |
| 披露口径 | 明确标注「相关性百分比属于模型主观推断，非事实核验」 | — |

## 2. 定位差异：先排除不可比的部分

- **浅层聚合 vs 深研循环。** jev-search 到 SERP 链接级为止，不深读、不交叉、不综合；谛听的价值在深研循环（scrape → 交叉验真 → 综合报告）。定位相反，**整体定位不学**。
- **技术栈不可迁移。** TanStack Start + React + Cloudflare Workers/KV/PWA，与我们的 Python（miroflow-agent / FastAPI / Gradio）栈无共享面，能借鉴的只有模式，不是代码。
- **KV 缓存 TTL 随时间窗浮动。** 模式本身好（时效敏感查询短 TTL、长青查询长 TTL），但只在 api-server 出现真实并发重复查询负载后才值得做，本期不做。

## 4. 不采纳清单

| 事项 | 理由 |
|---|---|
| 不生成总结答案的产品定位 | 与谛听深研报告定位相反 |
| TS / Cloudflare / PWA 技术栈 | 与 Python 栈无共享面 |
| KV 缓存 TTL 浮动 | api-server 无真实并发负载前不值得做 |
| 流式 NDJSON 事件协议（intent→found→lane→done） | gradio-demo 已有自己的进度事件体系；api-server 如需对外流式接口，届时再议，不在本次范围 |

## 5. 评审要点

## 6. 结论建议

M3 实现时参考其 URL 归一化与共识计数（B1）；M5/P1 设计 lane 结构时参考其单路超时隔离与路由表拆分（B2）；D1 维持暂缓，预算熔断记录为候选配套（B3）；M3 措辞采纳其披露口径（B4）；其余（定位、技术栈、KV 缓存、NDJSON 协议）不采纳。
