## 1. 对标对象概要

jev-search 是一个自然语言网页搜索引擎：LLM 解析用户意图 → 自动推演搜索词、数据源与时间范围 → 经 Search1API 并发检索多引擎 → 输出带相关性分数的链接与摘要。**明确承诺不生成总结性答案。**

与本文相关的工程特性：

| 特性 | jev-search 的做法 | 所在模块 |
|---|---|---|
| 多源并发 | Google/DuckDuckGo/Yandex/HN/Reddit/GitHub/X/arXiv/YouTube/Wikipedia/IMDb/WeChat 并行探测；单路限时 15s、全局 30s；单路超时不阻断全局 | `pipeline.ts` |
| 引擎路由 | 支持站点清单、引擎路由表、时间粒度配置独立维护 | `sources.ts` / `candidates.ts` |
| 猜测性请求 | 意图解析完成前即可预启 Google 搜索 | — |
| 共识度排序 | 结果按 URL 归一去重后，依「相关性 + 跨引擎共识度 + 原榜单位置」三维加权；低分结果隔离 | `rank.ts` / `merge.ts` |
| 供应商容错 | 三级模型供应商池（TypeSafe / Vercel Gateway / CF Workers AI），仅 402/429/5xx 触发软切换。**v2 更正：其回退并非总预算熔断，jev-search 不提供该能力** | `judge-config.ts` |
| 缓存 | KV 存中间态，TTL 随查询时间窗浮动（10 分钟–6 小时）。**v2 更正：cacheKey 为查询文本直接拼接，并非派生哈希**（v1 描述有误） | `cache.ts` |
| 披露口径 | 明确标注「相关性百分比属于模型主观推断，非事实核验」 | — |

## 2. 定位差异：先排除不可比的部分

- **浅层聚合 vs 深研循环。** jev-search 到 SERP 链接级为止，不深读、不交叉、不综合；谛听的价值在深研循环（scrape → 交叉验真 → 综合报告）。定位相反，**整体定位不学**。
- **技术栈不可迁移。** TanStack Start + React + Cloudflare Workers/KV/PWA，与我们的 Python（miroflow-agent / FastAPI / Gradio）栈无共享面，能借鉴的只有模式，不是代码。
- **KV 缓存 TTL 随时间窗浮动。** 模式本身好（时效敏感查询短 TTL、长青查询长 TTL），但只在 api-server 出现真实并发重复查询负载后才值得做，本期不做。

## 3. 可借鉴点（全部映射到路线图既有条目，不新开战线）

| # | 借鉴点 | jev-search 的做法 | 对应路线图条目 | 采纳建议（v2 按裁决修正） |
|---|---|---|---|---|
| B1 | **URL 归一化 + 共识计数** | URL 归一去重后按跨引擎共识度加权排序 | 路线图阶段 A（A-4 URL 规范化）与阶段 C（M3 结论核验） | **裁决：共识计数只是检索排序信号，不进入结论支持计数。** M3 计数口径 = 明确支持该主张的独立原始来源，v1 的「provider × 域名双维」提议作废。URL 归一化可参考但采保守规则：只处理 scheme/host 大小写、fragment、明确跟踪参数；**不照搬其对整个路径转小写**，不删可能区分内容的查询参数 |
| B2 | **多源并发 lane 架构** | 单路超时隔离、引擎路由表独立维护、意图未出先发猜测性请求 | 路线图并行轨道（M5 配置自适应）；规划项 P1 全源情报 | lane 抽象可参考：每源独立超时与失败隔离，天然满足「缺配置安全降级」。P1 图像搜索本质也是新增一条 lane。**裁决：猜测性请求在低配环境消耗配额，先测收益再开**；若 M5 实现多源档位，可在多源档单独评估 |
| B3 | **预算熔断**（v2 重新定位） | **jev-search 不提供总预算熔断**——其回退仅是 402/429/5xx 供应商软切换（v1 彏述有误，已更正） | 路线图暂缓项 D1 递归顺藤摸瓜 | 预算熔断是**我们自行设计的候选功能**，不是对标对象已有的能力。glm-5.3-flash thinking token 计费是 D1 搁置的成本顾虑；预算熔断是让深度扇出成本可控的候选配套，但不解决 D1 的另外两个顾虑（时延、质量增益无证据），**D1 维持暂缓**，此条仅作为未来重新立项时的配套候选记录在案 |
| B4 | **披露口径** | 「相关性百分比属于模型主观推断，非事实核验」 | 路线图阶段 C（M3 落地措辞） | M3 落地时把「模型打的分」（如 `_evaluate_confidence` 的 0-1 置信分）与「独立来源计数」分开标注，不混进同一个「置信度」标签。与验真品牌定位一致 |

## 4. 不采纳清单

| 事项 | 理由 |
|---|---|
| 不生成总结答案的产品定位 | 与谛听深研报告定位相反 |
| TS / Cloudflare / PWA 技术栈 | 与 Python 栈无共享面 |
| KV 缓存 TTL 浮动 | api-server 无真实并发负载前不值得做 |
| 流式 NDJSON 事件协议（intent→found→lane→done） | gradio-demo 已有自己的进度事件体系；api-server 如需对外流式接口，届时再议，不在本次范围 |

## 5. 评审裁决记录（2026-09-24，v1 评审要点全部有结论）

1. **B1/B2 已写入路线图**：URL 保守归一化进路线图阶段 A（A-4），lane 结构参考进并行轨道（M5），不新开条目。
2. **M3 计数口径**：v1 提议的「provider × 域名双维」**作废**；裁决为「明确支持该主张的独立原始来源」，跨引擎共识只作排序信号。
3. **猜测性请求**：低配环境消耗配额，**先测收益再开**；多源档位实现后可单独评估。
4. **B3 预算熔断**：已记录为 D1 重新立项时的配套候选；同时更正事实——该能力 jev-search 并未提供，属我们自行设计。

## 6. 结论建议（v2）

M3 实现时参考其 URL 归一化（采保守规则，共识计数只作排序信号）；M5/P1 设计 lane 结构时参考其单路超时隔离与路由表拆分；D1 维持暂缓，预算熔断（我们自行设计的候选功能）记录为配套；M3 措辞采纳其披露口径；猜测性请求先测收益再开。其余（定位、技术栈、KV 缓存、NDJSON 协议）不采纳。**两处事实更正随 v2 生效：cacheKey 为查询文本直接拼接；其供应商回退并非总预算熔断。**
